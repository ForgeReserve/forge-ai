# Payments

This document describes how Forge AI takes, holds and returns eCash, and what happens when something fails halfway.

## Units and precision

A token's unit is `usd` (amounts are cents) or `sat`. Internally every amount is tracked in **msub**, a thousandth of the unit: milli-cents for `usd`, millisatoshi for `sat`. Prices are set in USD per million tokens and computed in nano-USD, then rounded up once into msub.

- Balances keep sub-cent precision. A request that costs 0.164 cents takes 164 msub from the balance; a hundred of them take 16.4 cents, not a dollar.
- NUT-24 payments are whole tokens, so a per-request charge rounds up to a whole cent or sat. The rest comes back as change.
- Withdrawals are whole units. A sub-unit remainder stays on the balance.
- Sat prices use the median BTC/USD rate from at least `FORGE_RATE_MIN_SOURCES` sources, cached for `FORGE_RATE_TTL_SECONDS`. If sources fail, the last good rate is used until it is `FORGE_RATE_MAX_STALE_SECONDS` old; after that, sat requests get HTTP 503 and USD keeps working. Within one request, reservation and settlement use the same rate.

## Accepting a token

Every token is checked before the mint is contacted: it must be `cashuB`, under `FORGE_MAX_TOKEN_BYTES`, from a trusted mint (URL compared after normalization), in an accepted unit, with proofs from that mint's keysets for that unit, and worth enough after input fees. Failures are HTTP 400 with `untrusted_mint`, `wrong_unit`, `insufficient_amount` or `invalid_token`, and the token is left untouched.

The token is then swapped at the mint into new proofs that only the gateway knows. A token the mint reports as spent is `token_spent` (400).

## Flow 1: NUT-24 per request

1. Client sends the request with no credentials.
2. The gateway prices the worst case (the funds hold, below): input tokens estimated as `body bytes / FORGE_BYTES_PER_TOKEN` (default 2, deliberately high) plus `max_tokens` at the output price. It answers `402` with `X-Cashu: creqA...`, a NUT-18 request with `a` (amount), `u` (unit), `m` (trusted mints), `s: true` and `i`, the request id, which is also in the `X-Forge-Request-Id` header. Sat quotes carry `FORGE_SAT_PRICE_BUFFER` headroom.
3. Client retries with `X-Cashu: cashuB...` and `X-Forge-Request-Id` set to that id (and `X-Forge-Invite` while invite-only). The paid request then runs under the id the client already holds, so its change stays findable at `GET /v1/change/{request_id}` even when the paid response is lost and error or startup recovery owes the change. Each id can be used for one paid attempt, even one that fails: an id that already has a request is `409 request_id_used`, before the token is touched; a malformed id is `400`. A retry without the header gets a new id, returned in `X-Forge-Request-Id`.
4. The gateway re-prices, checks the token covers it, swaps it, calls the supplier, and charges `ceil(actual cost)` capped at the hold (and so at what was paid).
5. Change, if any, is issued as a new token from the same mint: in the `X-Cashu-Change` response header for non-streaming responses, in the final `event: forge` of a stream, and always at `GET /v1/change/{request_id}`.

NUT-24 does not specify change. Forge AI's choice (header, final stream event, re-fetch URL) is documented here and in [API.md](API.md). Upstream failures charge nothing and return everything.

## Flow 2: prepaid balance

1. `POST /v1/wallet/topup` with a token, or Fedimint notes where the gateway takes them ([Fedimint notes](#fedimint-notes)), and an invite for a new balance. The gateway returns a new `sk-forge-...` key, or credits the key in `Authorization`. A client may also choose its own key (`sk-forge-` plus 24 to 64 URL-safe characters) so that a lost response never loses the key. A token in the other unit from the balance's is refused untouched (`wrong_unit`); it can be changed instead (Changing units, below).
2. Each request reserves its worst-case cost against the balance (`available = balance - active reservations`), runs, then settles: it charges the actual cost (capped at the reservation) and releases the rest. Settlement is idempotent.
3. `POST /v1/wallet/refund` debits whole units and issues a token. `GET /v1/wallet/refunds` re-delivers every token issued to the key.

Only a SHA-256 of each key is stored.

## Two balances

A balance has one unit for life, so the v2 app holds up to two: one in dollars and one in sats, each with its own balance key (owner decision, 2026-11-18). Money goes to the balance of its own unit, with no change of units and no fee, and each question is paid in full from one of them.

**The gateway rule** (`src/accounts.ts` `siblingProof`). While invite-only, a new balance needs an invite, or, at `POST /v1/wallet/open` only, an event pass use. A request that opens a balance (`POST /v1/wallet/topup`, `/v1/wallet/fund/lightning`, `/v1/wallet/fund/onchain`, `/v1/wallet/fund/foreign/quote`) may carry `X-Forge-Sibling: <key>` instead: the key of a balance the client holds in the other unit. That key opens the new balance, with no invite redeemed and no pass use counted, when its balance

- is a paid balance (a free-question balance proves nothing),
- is not frozen,
- is in the other unit,
- has at least one ledger line (it was funded, or opened with an invite or a pass at `POST /v1/wallet/open`), so `releaseIfEmpty` never deletes it and never gives its invite or pass use back,
- was not itself opened this way,
- and has not opened a balance this way yet.

Anything else is `403 sibling_refused`, and nothing is opened. The checks run before the transaction that creates the balance and again inside it, and a unique index on `accounts.sibling_of` backs the last one, so two requests at once cannot both pass.

The bound: each balance opened with an invite or a pass use (or before the gateway was invite-only) gains at most one balance in the other unit, and that one gains none. A key in the other unit never needs an invite nobody spent, and no chain of keys can open more. A balance opened this way whose first funding fails or expires is deleted by `releaseIfEmpty` like any other: it gives back nothing (it took no invite and no pass use), and the balance that opened it may open one again.

What is stored: one column, `accounts.sibling_of`, on the new balance only: the id of the balance whose key opened it. Nothing is written on that balance, and no key is stored, only the SHA-256 of the new key as for every balance. The bound needs that one link; with it, the operator can tell that the two balances belong together ([PRIVACY.md](PRIVACY.md)). The new balance's `invite_id` and `pass_id` stay empty. The ledger, the reservations and the fundings are those of two ordinary balances. While the gateway is not invite-only the header is not read, and nothing is stored. `GET /v1/wallet/fund/methods` lists `sibling: {enabled, header}`; a gateway without it opens a second balance only with an invite.

**The v2 app** (`public/v2/core/balances.js`, `app.js`):

- **Keys.** The first key stays where it always was, `forge.balanceKey` (or `forge.balanceKey@<engine>`), the Classic page's name, whatever its unit. The second is kept in `forge2.balanceKey2` (`@<engine>` likewise). A new key goes into the empty name and never over a key; a third one, which the app never asks for, would only be kept aside in the list `forge2.extraKeys`, which is added to and never written over. The engine says each key's unit (`GET /v1/wallet`). So a phone from before two balances keeps its key as the balance of its unit, and nothing is moved.
- **Where money goes** (`landsIn`). eCash, a paper note and a Cashu card: the balance of the token's unit, through `wallet.topup`. Lightning and a Fedimint card (its till pays a Lightning invoice): sats. On-chain: sats. With no balance in that unit, the app opens it: with the invite while it holds no balance at all, else with `X-Forge-Sibling` and the key it holds, so no invite is asked. For that second balance the app makes the key itself and keeps it (its storage name, and `forge2.newKeys` with its unit) before it sends anything, then sends it as the bearer with the header. An answer that never arrives costs nothing: the same key and the same eCash sent again find the balance the engine opened (a replay), where a key the engine made would be lost with the answer and the retry refused. A key so made that the engine does not know yet, or any more (its first funding failed and the engine deleted the empty balance), stays on the phone and opens the balance with the next money in its unit. Nothing is sent while the unit of a kept key is not known (the engine could not be read): the money waits on the phone and the screen says to try again, so a second balance is never opened in a unit the phone holds, and a refusal is never taken from a key sent by mistake. A request may carry an invite beside the header: the gateway uses the invite when it refuses the key. Only where the engine cannot (invite-only with no `sibling` in its methods, or a `sibling_refused`, which the app remembers until it is opened again), the money goes to the balance the phone has: eCash, notes and cards in the other unit through [Changing units](#changing-units), price first; Lightning and a Fedimint card in that balance's unit; on-chain is refused, as before.
- **Which balance pays** (`payUnit`). A question, a recording turned into text and an answer read aloud are each paid by the dollar balance when it covers the request's hold in dollars, else by the sat balance when it covers the hold in sats. The sat balance pays only while the app has a BTC/USD rate (`btc_usd` in `GET /v1/models`); without one only the dollars count. A request is never split: when neither balance covers it alone, the app says there are not enough funds and offers Add money, even when the two together would cover it. The price lines are in the unit of the balance that pays.
- **What is shown.** The home shows one total: one balance with money in its own unit, as before; both in dollars, the sats at the app's BTC/USD rate (rounded down); with no rate, the dollar balance, and the sats stay on Funds. Funds lists the two balances as rows, each with its own Take out, eCash in its unit, once both hold money; with one, Funds is as it was. The gold ring is the total over the sum of both full marks (each unit keeps its own, `peaks:<engine>` in IndexedDB; the one kept before two balances becomes the first key's). Questions left, and Playful's star chip, count whole typical questions in each balance at the model's price in its unit (sats only with a rate), added up.
- **A key the engine no longer knows.** Only a definite `401` from `GET /v1/wallet` lets a key go; a network error or a `5xx` changes nothing. The key is added to the list `forge2.unrecognizedKeys` (never written over). With one key, it is also kept in `forge.unrecognizedKey`, as before, with a message. With two, the one let go is a balance whose first funding failed (the engine deletes only those): it goes without a word, and the other key carries on. Erase everything names both balances that hold money and counts the keys kept aside, with Copy keys.
- **Per balance.** Refund records (`refundsShown:` and `refundsAwaited:` with the end of each key) and other-mint tokens on their way (looked up with the key of their balance's unit). Free voice questions are counted per balance on the gateway, so a phone with both balances has two daily allowances (`FORGE_FREE_VOICE_PER_DAY` each; the operator's daily budget still bounds them all); the app counts on the home balance's (dollars first). Freezing one balance does not freeze the other: the operator freezes each by its id (`accounts.sibling_of` shows which belong together). Free questions and event passes are unchanged; a pass opens a dollar balance.

## Free models

A model with `"pricing": "free"` in the catalog costs the user nothing. Every Token Factory model is free (owner decision, 2026-11-15): Token Factory charges Forge nothing during its beta. Each free model says why in `free_reason`.

- **Who can use one:** anyone with a balance key (`Authorization: Bearer sk-forge-...`) from a balance opened with an invite code, even with nothing on it, and not frozen. `POST /v1/wallet/open {"invite": "..."}` opens such a balance at 0 and returns its key; it always takes an invite, even with `FORGE_INVITE_ONLY=false`, so a free model is never open to people without one. An event pass works there too (and only there): one code that opens up to N such balances until it expires (docs/ADMIN.md, Event passes). Funds can be added to the same key later for the paid models. The address and key rate limits apply as on every request.
- **What it costs:** nothing. No reservation is made and nothing is charged, whatever the usage, at a balance of 0 or not, in usd or sat (no BTC/USD rate is needed). `FORGE_MARKUP` does not apply. The response carries `X-Forge-Charged-Msub: 0` and the balance; a stream's `forge` event says `charged_msub: 0`.
- **What is recorded:** the request is still metered in the `requests` table and the `request` log line like any other: tokens in and out, status, `charged_msub` 0, `price_nusd` 0, `supplier_cost_nusd` 0 and `cost_source: "free"`.
- **Without a balance key:** `401 balance_key_required` (with `WWW-Authenticate: Bearer`), before any payment is looked at. There is no 402 and no NUT-18 request, so a NUT-24 client has nothing to pay, and an `X-Cashu` token sent with the request is never read, swapped or kept: it stays the sender's. A free-question (credit) balance key is refused the same way, with `403 balance_key_required`: credits are not a balance key for this. A frozen balance gets `403 account_frozen`.
- **The catalog:** a free model carries no token price (`input_usd_per_mtok` and `output_usd_per_mtok` left out, or 0), needs `free_reason`, and cannot have `web_search` (a search has its own fee). The loader refuses anything else. Its hold is 0 whatever its supplier's schedule, and it is left off `FORGE_FREE_MODELS` (the free tier's list) even if named there.
- **`GET /v1/models`:** `pricing.free: true` and `pricing.free_reason` on a free model (`free: false` on the others). The older fields stay, all at 0: `usd_per_mtok` and `sat_per_mtok` are 0 in and 0 out, `mode` is `metered`, and `hold` is the metered shape with `input_nano_usd_per_token` and `output_nano_usd_per_token` 0 and `web_search: null`, so a client that does not know `free` computes a hold of 0 as well. `GET /v1/wallet/fund/methods` adds `open: {enabled, free_models}`.
- **The apps:** the v2 app's price line reads Free, the model list shows a Free badge, Funds says questions to the model are free, and "not enough funds" never stops one. An invite code alone opens a $0 balance from the app: Start free on the first run's last step (Private only; moved from Welcome on 2026-11-15 so that the first run ends once the code is in) and in Add money (owner decision, 2026-11-15); the invite is spent exactly as a funded top-up spends it (the same open, redeemed and revoked rules, and the same address limit). With no balance key yet, Type and the home lead to Start free instead of Add funds, in Start free's words ("This model is free. Start free with your invite code."), with no word of a balance. Start free is easy to find (owner, 2026-11-15, for people at an event with an invite code and no money): while the engine has free models, the last first-run step has one button, the round one, green, which opens a Start free sheet (owner, 2026-11-16: both choices are on the sheet), with Listen and Scan (the camera reads a printed code or an event's QR link, `core/join.js` `codeFrom`); the question's answer ends the first run on the home, and "I'll add money instead" ends it on Add money, on the paper note's card, Add money (the wallet cards, `public/v2/screens/wallet.js`) shows the Start free card first while there is no key or a $0 balance on a paid model and opens Start free's own screen (`#/funds/start-free`: the code with Paste and Scan, then the question; the yes ends on Funds, whose ring then says FREE beside Ask now), and Type's funds notice offers "Use a free model instead" next to Add funds (`public/v2/screens/startfree.js`). The home at $0 on a free model shows the model's name with FREE and a small Add money button. The free models are Standard models, so with Private only on (the default) the app asks once, in plain words, before using them: "Use free models" turns Private only off and chooses a free model (`glm-5.3-flash` when listed, else the first free one, `core/price.js` `freeModelChoice`); "Keep Private only" leaves it on and says where to change it. Private only is never turned off without that yes. The v1 app's model menu reads Free.

These are not the free tier's free questions ([FREE-TIER.md](FREE-TIER.md)): those are credits on a free balance of their own, one per question, on the models in `FORGE_FREE_MODELS`. A free model is a kind of model; a free question is a kind of balance.

## Free voice questions

Hold to talk works on a balance with nothing on it (owner decision, 2026-11-15): the operator pays for turning the recording into text, within two daily limits. Speech output (`POST /v1/audio/speech`) is never free.

- **Who gets one:** a transcription (`POST /v1/audio/transcriptions`) from a balance key whose available funds are below the request's price, such as a $0 balance opened with an invite code for the free models. The balance must not be frozen (`403 account_frozen`). A free-question (credit) balance takes no speech to text at all (`403 not_free_model`), as before. A balance that can pay keeps paying exactly as before, and its allowance is not touched.
- **The limits, per UTC day:** `FORGE_FREE_VOICE_PER_DAY` (default 20) per balance, and the operator's budget `FORGE_FREE_VOICE_BUDGET_USD` (default 5.00 USD) for all balances together, counted at the supplier's cost (the catalog's `request_usd` plus `usd_per_second`, without `FORGE_MARKUP`; $0.01 for `tinfoil/whisper-large-v3-turbo`, so $5.00 pays for 500). Either set to 0 turns free voice questions off, and a balance short of the price gets `402 insufficient_balance` as before. Both start again at midnight UTC.
- **Used up:** `402 free_voice_limit`, before the supplier is called, with `Retry-After` (seconds to midnight UTC) and `free_voice: {enabled, per_day, left: 0, resets_at, reason}`; `reason` is `allowance` (this balance used its share today) or `budget` (the day's budget cannot pay for one more). Nothing is charged.
- **What it costs the user:** nothing. Nothing is held or charged; the response carries `X-Forge-Charged-Msub: 0`, the balance, and `X-Forge-Free-Voice-Left` (what the balance has left today). A transcription that fails is not counted against either limit.
- **What is recorded:** the request is metered in the `requests` table and the `audio` log line like any other, with `reserved_msub` 0, `charged_msub` 0, `price_nusd` 0, `supplier_cost_nusd` the supplier's cost and `cost_source: "operator"` (the log line adds `free_voice: true`). The admin page's supplier costs count it as a cost with no revenue.
- **What is stored to count them** (`src/free-voice.ts`): per UTC day, the number served free and their summed supplier cost (`free_voice_days`), and per balance that used one today, a count keyed by an HMAC of the balance id (`free_voice_uses`). The HMAC key is random, made for the day and kept in that day's row so a restart does not reset the counts. When a new day starts, the old day's per-balance counts are deleted and its key is set to NULL: a past day keeps only its two totals. No time of a request, no audio and no text are stored there. (The `requests` row above still names the balance, as for every request.) A request takes its place in both counts before the supplier is called, so requests sent at once cannot each pass a limit, and gives it back if the supplier fails.
- **For the app:** `GET /v1/wallet` reports `free_voice: {enabled, per_day, left, resets_at, reason?}` for the key, so the app can tell before recording; `GET /v1/wallet/fund/methods` adds `free_voice: {enabled, per_day}`. The v2 app records and sends on a balance that cannot pay while `left` is above 0 (no "add funds"), and the price line reads Free when the question itself is free too. Used up, it says "Free voice questions are used up for today. Type instead, or add funds." Typing is not affected.

## The funds hold

Before a request is sent on, the gateway holds the most it can cost (a balance reservation, or the NUT-24 quote):

- `pricing: "metered"`: the model's own metered worst case, at the model's prices with `FORGE_MARKUP`: input estimated as `ceil(body bytes / FORGE_BYTES_PER_TOKEN)` plus `max_tokens` (or `X-Tinfoil-Max-Output-Tokens`) of output. For an encrypted request the body bytes are the ciphertext the gateway receives.
- `pricing: "flat"`: the flat schedule, a request-size bucket plus declared max output at the schedule's output price.
- A free model (`"pricing": "free"` on the model, above): 0. Nothing is held.

No request is ever charged more than its hold, on any payment path; a usage figure above it is logged as `usage_over_reservation` and charged at the hold.

Until 2026-11-14 a metered supplier that also carried a flat schedule held the larger of the two. For `tinfoil/gpt-oss-120b` at 4,096 output tokens that held about 156 sat for a question charged about 0.1 sat, and refused a person with 124 sat. A flat schedule on a metered supplier is now ignored, for the hold and for the charge.

`GET /v1/models` lists each model's hold figures under `pricing.hold`, integers in nano-USD with the markup applied (`basis`, `bytes_per_token`, `input_nano_usd_per_token`, `output_nano_usd_per_token`; for a flat supplier `buckets` and `output_nano_usd_per_token`). The v2 app computes the same hold from them (`public/v2/core/price.js` `holdMsub`), shows it as the price line, and says "Not enough funds for this question" before sending when the funds not already held do not cover it. A sat hold also depends on the BTC/USD rate: the app uses `btc_usd` from the same listing, and the two agree to the msat while the gateway's rate has not moved since.

## Web search

Tinfoil's private models can search the web from the enclave (docs.tinfoil.sh/guides/web-search): `web_search_options` in a chat completion turns it on, `pii_check_options` takes detected personal details out of the search before it leaves, and `prompt_injection_check_options` drops planted instructions from what comes back. Tinfoil charges a fee once per request that searched, 0.05 USD (`requestPrice` of the Private Web Search tool at https://api.tinfoil.sh/api/config/models, read 2026-11-14), and reports the searches as `web_search_calls` in `X-Tinfoil-Usage-Metrics` (with `cost_usd` including the fee, and `other_cost_usd` for the privacy filter's own fee). No fee applies when the model did not search, even with search on.

- **Which models:** a model with `web_search: true` in the catalog, on a metered Tinfoil supplier with a `web_search` block. The shipped catalog turns it on for the six Tinfoil chat models, all listed with `toolCalling: true` in that config. `GET /v1/models` says which in `capabilities.web_search`.
- **Declaring it:** the gateway cannot read an encrypted body, so the client sends `X-Forge-Web-Search: 1` with it. A plaintext body is read: `web_search_options` in it turns search on. Search on a model that cannot search is `400 web_search_unavailable`; on a free balance, `403 web_search_not_free`.
- **The hold** with search on is the model's metered worst case plus the search fee and the search allowance (`extra_input_tokens` more input, `output_factor` times the output limit: a search adds results to the input and runs several model calls, each with its own output limit). The allowance is Forge's own figure (16,000 tokens and 2 in the shipped catalog), not Tinfoil's. `pricing.hold.web_search` lists the fee and the allowance, so the app shows the same hold.
- **The charge** is the reported tokens at the model's prices, plus the fee when `web_search_calls` shows a search, plus `other_cost_usd`, all with markup, never more than the hold. A search that was not declared is not in the hold: it is charged at most the hold and logged as `web_search_undeclared`. A plaintext stream never shows Tinfoil's metrics (they come in an HTTP trailer the gateway's fetch cannot read), so with search on the fee is charged there; a plaintext non-streaming answer and an encrypted one carry the metrics.
- **Not covered:** the cost of the prompt-injection check, which Tinfoil does not list separately (a run of its safeguard model over the results); if Tinfoil bills it inside `other_cost_usd`, it is passed on, otherwise the operator carries it.

## Cached input

Tinfoil keeps a prompt cache: when a request to a model starts with the same prompt as a recent one (a few thousand characters or more, such as the earlier turns of a conversation), Tinfoil can reuse that part, and on some models it bills those input tokens at a lower published price (`cachedInputTokenPricePer1M` in its rate card, docs.tinfoil.sh/sdk/prompt-caching). It reports how many input tokens were cached as `usage.prompt_tokens_details.cached_tokens` in the answer (in a stream, the usage chunk) and as `cached_prompt_tokens` in `X-Tinfoil-Usage-Metrics`. Both are part of `prompt_tokens`.

- **The catalog:** `cached_input_usd_per_mtok` on a model is the supplier's price per million cached input tokens, at most `input_usd_per_mtok`. The shipped catalog sets it for the three Tinfoil models whose rate card listed one on 2026-11-20: DeepSeek V4.1 Flash 0.01 USD (0.60 uncached), GLM 5.3 0.45 (1.80) and Kimi K3.1 Pro 0.40 (4.00). A model without it charges cached input at the input price.
- **The hold** stays at the full input price: whether the cache is used is known only from the answer.
- **The charge:** the cached tokens at the cached price and the rest of the input at the input price, with `FORGE_MARKUP`, rounded as every other charge (each price per token rounded up to a whole nano-USD, the total rounded up once into msub). It is never more than the same request would cost without the cache. What the hold does not use comes back as any unused hold does: to the balance, or as NUT-24 change.
- **Where the count comes from:** a plaintext answer's `usage`, else the usage metrics of a plaintext answer that is not streamed; the usage metrics header or trailer of an encrypted answer. A count that is missing or not a whole number is taken as no cached tokens, and one above the input tokens as all of them, so a wrong figure charges at most the full input price and never less than the cached price.
- **What the person sees:** the supplier's `usage` reaches the client as the supplier sent it, `prompt_tokens_details.cached_tokens` included. `GET /v1/models` lists `pricing.usd_per_mtok.cached_input` and `pricing.sat_per_mtok.cached_input` on a model with a cached price.
- **What the operator sees:** the request row and the `request` log line carry `cached_input_tokens`. The admin cost view counts cached tokens at the cached price on both sides: in the price people paid, and in the cost, which is Tinfoil's own `cost_usd` (it prices cached input at its cached rate) or else the usage at catalog cost. At markup 1 the two are equal. When Tinfoil's `cost_usd` differs from the catalog cost of the same usage by more than 1 percent, the gateway logs `supplier_cost_differs` with both figures and the token counts, and the charge stays at the catalog price.
- **Other suppliers:** a supplier that reports `prompt_tokens_details.cached_tokens` is read the same way. A model without a cached price charges as before.

## Metering

- Plaintext requests: the gateway asks the supplier for usage (`stream_options.include_usage` on streams) and settles on it. If the client did not ask for usage, the usage-only chunk is removed from the stream it sees.
- No usage reported on a plaintext stream: the gateway counted the answer as it passed, so input is estimated as `body bytes / 4` and output from the stream (at least one token per content chunk, or characters / 4 if larger), at most the hold.
- No usage reported on a complete non-streaming or encrypted response (nothing the gateway could count): the metered worst case is charged, which is the hold.
- A non-streaming response, plaintext or encrypted, whose body fails to arrive after `200` headers is an upstream failure, settled before the error is returned: `502`, nothing charged, the reservation released and, for NUT-24, the full change in `X-Cashu-Change` and at `GET /v1/change/{request_id}` at once.
- Client disconnects mid-stream: the gateway aborts the upstream call and settles on what was produced so far, using upstream usage if it arrived, else the estimate above.
- Encrypted pass-through: see PRIVACY.md. Usage comes from Tinfoil's `X-Tinfoil-Usage-Metrics` header or trailer; without it a complete answer is charged the metered worst case (the hold), and a stream cut off midway is charged the input estimate plus one token per frame it carried.
- `pricing: "flat"` suppliers always charge the flat schedule: a request-size bucket plus declared max output tokens.

## Flow 3: funding a balance through the Forge mint

For users who do not hold Forge eCash yet. In every method the gateway mints Forge eCash into its own wallet with deterministic (NUT-13) outputs and credits the balance with exactly the minted amount, in the same SQLite transaction that stores the proofs. A new balance needs an invite while invite-only; it is created (and the invite bound to it) when the first quote is made, and released again, with the invite reopened, if that funding expires or fails before anything is credited.

### Lightning

1. `POST /v1/wallet/fund/lightning {amount, unit}`: the gateway asks the Forge mint for a NUT-04 bolt11 mint quote in the balance unit, stores it (`fundings` row, `state=pending`) and only then returns the invoice.
2. A poller (every 3 s for the first 10 minutes, then every 30 s) and every status request ask the mint for the quote state.
3. On `PAID`: prepare the mint with deterministic outputs, store the outputs and the counter range (`state=minting`), call `POST /v1/mint/bolt11`.
4. One transaction: proofs stored, balance credited `amount`, `state=done`.
5. Unpaid a minute past the quote's expiry: `state=expired`.

### On-chain (NUT-30)

The Forge mint advertises `onchain` (sat) in NUT-04 on its Nutshell on-chain branch. The shapes used here come from that branch's source (`cashu/payment/onchain.py`, `cashu/core/models/mint_quote.py`): `POST /v1/mint/quote/onchain {unit, pubkey}` returns a reusable address with `amount_paid` and `amount_issued` and no expiry; `POST /v1/mint/onchain {quote, outputs, signature}` mints. The quote is locked (NUT-20) to a key the gateway generates per funding, so only the gateway can mint it.

1. `POST /v1/wallet/fund/onchain`: quote created and stored, address returned.
2. The poller checks the quote every minute. Whenever `amount_paid > amount_issued`, it mints the difference (same steps 3 and 4 as Lightning, signed for the quote key) and credits it. The address stays watched for `FORGE_ONCHAIN_WATCH_DAYS`, so later deposits are credited too.
3. The mint decides when a deposit counts as paid (Forge: after its deposit wallet sees the configured confirmations). `FORGE_ONCHAIN_CONFIRMATIONS` is only what users are told. With `FORGE_ESPLORA_URL` set the status also shows unconfirmed and confirmed amounts seen on chain.

`FORGE_ONCHAIN_ENABLED` is `false` by default: the flow is tested against a mock that follows those shapes (`test/e2e/onchain-mock.ts`), not against the live mint. Turn it on after one small live deposit.

### eCash from another mint

1. `POST /v1/wallet/fund/foreign/quote {token, unit}`. Policy first: foreign funding enabled, the mint is not one of ours (`use_topup` in the balance's unit; in the other unit see Changing units, below), is accepted by `FORGE_FOREIGN_POLICY` (`discovered`: the operator list, meaning `FORGE_FOREIGN_ALLOW` and mints added on the admin page, or the NIP-87 discovered list; `allowlist`: the operator list only; `any`: every mint, or `FORGE_FOREIGN_ALLOW` when set) and is not in `FORGE_FOREIGN_DENY` (`mint_not_allowed`, with a pointer to `GET /v1/wallet/fund/mints`), is `https` and resolves to public addresses only (SSRF guard), and the token is at most `FORGE_FOREIGN_MAX_SAT` / `_USD`. Then pricing: the gateway creates a Forge bolt11 mint quote for a credit and a melt quote for that invoice at the token's mint, shrinking the credit until the melt amount, its fee reserve and both input fees fit the token. Nothing is spent. The response shows the token amount, the exact credit and the most the token's mint can keep (`fee_max`).
   - **Unlisted mints.** Under `discovered` and `allowlist` with `FORGE_FOREIGN_UNLISTED=true`, a mint that is not accepted (and not denied, and not Forge's) passes the URL safety check and then answers 409 `mint_unlisted` with `{unlisted: {mint, max: {sat, usd}}}`. The same request with `accept_unlisted: true` goes ahead once the mint passes the live probe discovery uses (cached 10 minutes, a failure 1 minute; a failure answers `mint_check_failed`). The token is then capped at `FORGE_FOREIGN_UNLISTED_MAX_SAT` / `_USD` (cents) as well as the other-mint cap (`amount_too_large`), and the funding row records `f_unlisted = 1`. With `FORGE_FOREIGN_UNLISTED=false` such a mint gets `mint_not_allowed`. Policy `any` never asks. `GET /v1/wallet/fund/methods` shows `foreign.unlisted: {enabled, max: {sat, usd}}`.
2. `POST /v1/wallet/fund/foreign/confirm {id, token}`: before any mint is loaded or contacted, the token must name the quoted mint (normalised) and unit; otherwise 400 `token_mismatch` and the funding stays `quoted`. It must then be the quoted token by the hash of its secrets (also `token_mismatch`). It is received at its own mint through the normal receive path (`incoming` row, NUT-19/NUT-09 recoverable). The new proofs are stored `reserved` for this funding and never used for payouts.
   - **Every contact with another mint is vetted.** The wallet runs the URL safety check (https, public addresses only, unless `FORGE_FOREIGN_ALLOW_INSECURE`) each time it loads the wallet of a mint outside `FORGE_TRUSTED_MINTS`, cached or not: quote, confirm, melt, refunds, change and recovery. A refusal answers `mint_not_allowed`; a step that already holds the eCash stays where it is and is retried by the poller. Confirm then answers 200 with the in-progress state (`melting`) for the client to poll, never an error, since the token is already taken. No Cashu request follows a redirect (cashu-ts `redirect: "error"` for the whole process, set in `src/cashu/wallet.ts`), so discovery, keysets, keys, swap, melt and the checks only ever reach the vetted address.
3. Melt: deterministic NUT-08 blank outputs and the counter range are stored before `POST /v1/melt/bolt11`. If the melt quote expired meanwhile, a new one is made for the same invoice; if it no longer fits, the held eCash goes back to the user as a token from their mint (`refund_token`, `state=refunded`).
4. Melt paid: the unused fee reserve comes back as change signatures, which are returned to the user as `change_token`. The funding then continues as a Lightning funding whose invoice is already paid: mint at Forge, credit `credit`.

The balance unit and the token unit may differ (a sat token can fund a usd balance); the quote uses the mint's own conversion through the Forge invoice.

**The v2 app** prices it in the eCash box, where any eCash is pasted or scanned: a token the phone reads as from a mint the engine does not take (`core/note.js` `noteVerdict`) goes to the quote instead of the top-up, and so does one the top-up refuses with `untrusted_mint`. Over `foreign.max` in its unit (or the `unlisted.max` a `mint_unlisted` answer carries) it says so and asks no price. The price card shows the amount added, where it comes from (`token_amount`) and `fee_max`, with Add and Keep my eCash; Add holds the token in the vault before confirm (`modules/fund/kit.js` `foreignQuote`). The separate Other mint screen is gone ([APP.md](APP.md#fedimint-notes-in-the-ecash-box) covers the box).

### Changing units

A balance has one unit for life. eCash from one of Forge's own mints (`FORGE_TRUSTED_MINTS`) in the balance's unit is a top-up: received as it is, with no fee beyond the mint's input fee. In the other unit (sat eCash for a usd balance, or usd eCash for a sat balance) it is changed through the other-mint path above, with its state machine and its rows. `FORGE_CONVERT_ENABLED` (default `true`) turns it on; `GET /v1/wallet/fund/methods` shows `convert: {enabled, units}`.

- **The top-up says where to go.** `POST /v1/wallet/topup` with such a token still answers `400 wrong_unit` with the same message, before the mint is contacted, and adds `convert: {quote: "/v1/wallet/fund/foreign/quote", unit, token_unit}` (`unit` is the balance's) while the change is on for that unit. Nothing is ever changed without the quote.
- **The quote.** `POST /v1/wallet/fund/foreign/quote {token, unit}` with the balance's unit. The token is read as a top-up reads it (a trusted mint, a unit in `FORGE_UNITS`). The other-mint rules are about trusting another mint and do not apply: not `FORGE_FOREIGN_ENABLED`, the policy, the deny list, the URL safety check, `FORGE_FOREIGN_MAX_*` or the unlisted caps. The credit is a Lightning funding in the balance's unit, so the Lightning limits of that unit apply to it: at most `lightning.max` (`FORGE_FUND_MAX_SAT` / `_USD` and the mint's own maximum, `amount_too_large`) and at least `lightning.min` (`insufficient_amount`). Credits are never money (`credits_not_money`, since the credit mint is never trusted), and a free balance answers `409 wrong_balance`. The answer carries `foreign.convert: true`.
- **The rate is the mint's.** The gateway's BTC/USD rate, less 3 percent, only picks the first credit to try (`rate_unavailable` without one). The Forge mint turns that credit into a bolt11 invoice in the balance's unit, and the token's mint quotes the melt of that invoice in the token's unit, with its fee reserve. The credit shrinks until the melt, its fee reserve and the input fees fit the token, then is asked once more at the price the mint just quoted (credit times what the token can spend, over the melt's cost, within the limit), so that less of the token comes back as change in a unit the balance does not hold. The credit is always the amount of a Forge invoice the token's mint has quoted.
- **Fees the person pays.** The token's mint's input fees (when the gateway receives the token and when it melts it), and the Lightning fee of the melt, at most its fee reserve. All are inside `fee_max`, shown before the person agrees. What the fee reserve does not use, and any part of the token the credit leaves, comes back as `change_token`: eCash from the token's mint, in the token's unit. Forge takes no fee. A difference between the mint's two prices (what it asks in one unit to pay its own invoice in the other) is the mint's.
- **Confirm, recovery and the outcome** are other-mint funding's, state for state (`quoted`, `receiving`, `melting`, `pending`, `minting`, `done`, or `refunded` with `refund_token`), with the same crash safety (below). The received proofs are held `reserved` for the funding, never used for payouts, and spent by the melt. A token taken by one funding or top-up is `token_spent` everywhere else.
- **The v2 app.** The app changes units only where it cannot open the balance of the token's unit ([Two balances](#two-balances)): an engine without `sibling`, or one that refused it. Then the eCash screen reads a pasted or scanned token's mint and unit before sending it (`core/note.js` `noteVerdict`, `convert`). From the engine's own mint, in the unit the funds do not hold, while `convert.units` lists the funds' unit, it asks for the quote instead of adding it, and shows the price in the eCash box (`modules/fund/kit.js` `foreignQuote`): what is changed into what, the amount added in big type, where it comes from, the most the fees take, then Add (a yes) and Keep my eCash (a no). A no sends nothing and keeps nothing: the token stays in the box, unspent. A yes holds the token in the vault before confirm, as eCash from another mint does, and the screen ends on "Added ...". A top-up the engine refuses with `wrong_unit` and `convert` (a token the phone could not read) gets the same offer. A scanned paper note in the other unit says so and offers See the price, which opens the eCash screen with it; a Cashu card tap goes the same way (above). Lightning and a Fedimint card cannot meet the mismatch: their invoice is asked in sats for the sat balance, or, where it cannot be opened, in the funds' unit.

**When the token's mint is the Forge mint.** The Forge mint then pays an invoice it issued itself. Nutshell (read in 0.22.1, `cashu/mint/ledger.py`: `melt_quote` and `melt_mint_settle_internally`) settles a melt internally, with no Lightning payment and a fee reserve of 0, only when the invoice's mint quote has the melt's unit. A mint quote in the other unit is never settled internally: the melt goes to the Lightning backend of the token's unit, which pays the invoice made by the backend of the balance's unit as an ordinary Lightning payment, with that backend's usual fee reserve. Whether that payment goes through depends on the mint's setup. Where the two units are served by different Lightning wallets, it is a payment between them. Where one Lightning node serves both, it is a payment to itself, which many nodes refuse; the melt then fails, is tried once more, and the token's value comes back as `refund_token`, less the input fees. No eCash protocol swap moves value between two units: NUT-03 swaps keep one unit, so a melt into an invoice is the only way through a mint. The local test mints (Nutshell 0.22.1 with FakeWallet backends) pay every invoice without moving money and auto-pay every invoice they issue, so `test/e2e/convert.e2e.test.ts` proves the gateway's states, limits, recovery and arithmetic against the mints' real quotes; the Lightning payment between a mint's two units is not tested there. Try one small change each way on a live mint before relying on it.

### Crash safety

| State | What is stored | If the process dies here |
| - | - | - |
| `pending` | quote id and invoice/address, before the client sees them | The poller resumes the quote on restart |
| `minting` | outputs (serialized) and counter range, before `POST /v1/mint/...` | Replay the identical mint (NUT-19, cached for bolt11 at Forge); else restore the counter range (NUT-09); else, if the quote is still mintable, mint with the same outputs. Credited once |
| `quoted` | the plan, not the token | Nothing spent; the client keeps the token. Expires with the quotes |
| `receiving` | the `incoming` row | `prepared`: replayed or restored now or at startup; `new`: back to `quoted`; rejected: `failed` |
| `melting` | blank outputs and counter range, before `POST /v1/melt/bolt11` | Melt quote `PAID`: change from the quote's signatures or from restore, then mint. `UNPAID` with inputs unspent: retry once, then refund. `PENDING`: wait |

Finalizing a mint runs in one transaction that checks the funding is still `minting` with the same stored outputs, so two pollers, a status request and a restart can race and the balance is credited once. The e2e suite injects faults after the mint, after the foreign swap and after the melt, restarts on the same database (with and without NUT-19 replay) and checks the credit is exact and single. `test/e2e/convert.e2e.test.ts` does the same for a change of units at each state (`quoted`, `receiving`, `melting`, `pending`, `minting`, `done`).

### A Cashu card (the v2 Android app)

A Cashu card (the card protocol 2.0 from the cashu-javacard applet, as flash-pos speaks it) holds pieces of eCash locked to the card's own key with `SIG_ALL`, and pays with one BIP-340 signature over a whole swap. The phone takes eCash off it in one tap where the card stays on the phone (`public/v2/core/card/`, ported from flash-pos `src/services/cashuCard.ts`):

1. Read: `SELECT`, `GET_INFO`, `GET_CARD` (the mint, the unit, the refund key), `GET_PUBKEY` and `AUTH` (the card proves it holds that key), then the short listing of its pieces (`GET_PIECES`) and its open change outputs (`GET_CHANGE`).
2. The card's mint, through the engine: `POST /v1/wallet/fund/card/mint {mint, unit}` answers its keysets and the active keys. The engine reaches the mint only if it is the engine's own (an alias goes to the main address) or passes the other-mint checks (`vetForeignMint`: the policy, the URL safety check, the unlisted prompt with `accept_unlisted`). The credit mint is refused.
3. Plan: the pieces of one date that cover the amount (all of the largest group by default), the mint's input fee paid from the amount moved, the phone's outputs in powers of two, and the card's change. Change is made in the payment's keyset, so a card whose keyset is no longer active can move all of it only.
4. Pay: `VERIFY_PIN` (a wrong PIN answers `63CX`, the tries left), then the phone makes its outputs and blinding factors, `SPEND_ALL_BEGIN` with the slots, `SPEND_ALL_OUTPUTS`, `SPEND_ALL_CHANGE` for each change amount (the card makes those outputs itself), and **only after all of that is written to the phone's storage and read back**, `SPEND_ALL_SIGN`. The card burns its pieces in the commit that releases the signature. The signature is checked against the payment's message and stored at once.
5. Swap: `POST /v1/wallet/fund/card/swap {mint, inputs, outputs}`; the engine passes it to `<mint>/v1/swap` and the answer back. The phone checks each blind signature's amount, keyset and NUT-12 proof, unblinds its own outputs into a cashuB token (stored with the job before anything else), and loads the card's change back onto it (`GET_CHANGE` openings, `C = C_ - r·K`, `LOAD_PROOF`), in the same tap or the next one.
6. Add: a token from the engine's own mint goes through `wallet.topup` (stored in the vault first). A token from another mint is kept in the vault, marked not added, and the eCash box opens with it and shows its price (flow above). A card of the engine's own mint goes to the balance of its unit ([Two balances](#two-balances)). Only where that balance cannot be opened, a card in the unit the funds do not hold is refused before the tap, unless the engine changes units (`convert`): then its eCash comes to the phone the same way, kept in the vault, and the eCash screen opens with it and shows the price to change it (Changing units). A card has no limit for this beyond what it holds; a credit over the Lightning limit is refused at the quote and the eCash stays on the phone.

A broken tap is finished from what the phone holds:

| The card leaves | What the phone holds | What finishes it |
| - | - | - |
| before `SPEND_ALL_SIGN` reaches it | the payment | The next read finds the very same pieces (same `C`) still unspent in their slots and drops the payment. Nothing moved |
| after the commit, before the answer | the payment, without a signature | The next tap of that card: `SPEND_ALL_AGAIN` (with the PIN on a card that has one), checked against the stored payment, then the swap. This works only if the card comes back before it pays anywhere else: any later `SPEND_ALL_SIGN`, at a till for example, replaces the card's last signature, and then this payment cannot be finished |
| after the signature | the signed payment | The swap is sent again (now, on start, when the connection comes back, on Funds). If the mint already did it or is doing it (`11001`, `11002`, `11003`, `11004`), `POST /v1/wallet/fund/card/restore` (NUT-09) gets its signatures again |
| after the swap, before the change is loaded | the token, and the mint's signatures for the card's change | The token goes to the vault at once; the change is loaded at the next tap of that card (the change grant, or the PIN) |

A slot that is spent, empty, or holds another piece never drops a payment: the card's owner may have run `CLEAR_SPENT` and loaded new pieces into those slots. Then only `SPEND_ALL_AGAIN`, checked against the stored payment, decides.

A status word from `SPEND_ALL_SIGN` (`6A94` PIN needed, `6A8F` over the daily limit) is a refusal before the commit: nothing was burned and the payment is dropped. Any other failure there keeps it, and so does every failure after it. Only the card's mint refusing the swap with its own code (other than those above) marks the payment failed. An engine answer without a mint code (its other-mint checks, a setting changed, a mint that rate-limits or times out, which the relay answers as `503 mint_unavailable`) leaves the payment signed, and it is sent again later. A failed payment is listed on the Tap a card screen with its amount, its mint and what was said, and Try again sends the swap once more (or, with no signature, asks the card again at its next tap). Erase everything warns about it until it goes through.

For a card from another mint, `/v1/wallet/fund/card/mint` also answers `max`: the most other-mint funding takes from that mint in one token (`FORGE_FOREIGN_MAX_SAT` or `_USD`, and for an unlisted mint the lower unlisted cap). The phone never takes more than that off the card in one tap, and before the card signs it shows only what comes to the phone: the eCash box shows its own price next.

Not covered: the card's clock and limits (`SET_HEADER`, the no-PIN allowance), the owner's commands, a card's DLEQ store, the NFC tag application, and a 0.x or Foxy 1.x card, which is refused as needing an update before anything is asked of it.

### Fedimint notes

The gateway takes Fedimint eCash in the same top-up as Cashu once the operator turns it on: `FORGE_FEDIMINT_URL` and `FORGE_FEDIMINT_TOKEN` name the Fedimint receiver (`services/fedimint-receiver`, [FEDIMINT-RECEIVER.md](FEDIMINT-RECEIVER.md), where the steps to turn it on are). With `FORGE_FEDIMINT_URL` unset, nothing on this page changes: the gateway never asks a receiver and `GET /v1/wallet/fund/methods` has no `fedimint`. The gateway runs no Fedimint client itself; the receiver holds the notes, and the gateway keeps the balances (`src/fedimint.ts`).

**Which token is which.** `POST /v1/wallet/topup` reads `token` as before. Anything that starts with `cashu` (whatever comes before it is spaces, in any case) goes the Cashu way, exactly as without Fedimint. Anything else that looks like the notes the receiver reads, `fedimint` and base32 or base64 and base64url text (whitespace anywhere is ignored, as fedimint's own parsers ignore it), is Fedimint notes. The receiver decides whether it really is notes: text it cannot read is `400 invalid_token`.

**Where it lands.** Fedimint notes go to a sat balance only, credited in exact msat (a sat balance counts msat). Forge takes no fee. The federation charges its own fee to reissue the notes into the receiver's wallet, so the balance gets `net_msat` of the receiver's record, the notes' face value less that fee. A dollar key answers `400 wrong_unit`; with no key, the sat balance is opened as for Cashu (an invite while invite-only, or `X-Forge-Sibling`).

**A federation is accepted** only when it has a row in the gateway's `federations` table with state `active` (the operator joins it with `pnpm admin fedimint:join`) AND the receiver reports it joined. `pnpm admin fedimint:pause <id>` stops taking its notes at once, without leaving the federation; `fedimint:resume` takes them again. Notes already on their way when it is paused are finished.

**The steps.**

1. The gateway works out the notes' `notes_id` itself, with no network call, by the app's own reader (`public/v2/core/fedinote.js` `notesIdOf`: the module, the federation id's first 4 bytes and each note's public key, as the receiver computes it). If it already has a row `fm:<notes_id>`, these are notes sent before: the receiver is not asked to read them, and the top-up goes straight to that row (a replay, `token_spent`, `issuance_failed`, or, for a row still `prepared`, the receive asked about again, so `503 topup_pending` while the receiver is down). Notes with more than 256 notes in them, or that the reader does not read, skip this and are looked up by the receiver's `notes_id` after step 2.
2. `POST /parse` at the receiver: the notes' value, federation and `notes_id`, with nothing spent. The refusals below come here, before any balance is opened.
3. The balance is opened (or found), as for a Cashu top-up.
4. The gateway writes its own `incoming` row, id `fm:<notes_id>`, `purpose = 'fedimint'`, `status = 'prepared'`, holding the notes text, BEFORE it calls the receiver. The holdings cap is checked again in the same step.
5. `POST /receive` with the notes and this top-up's key, `forge:<balance id>`. The receiver answers the first caller's record to everyone: a record whose `key` is not this balance's means someone else gave those notes first, and the top-up is refused (`token_spent`), nothing credited.
6. Only a `done` record is credited: `net_msat` from it, in one transaction with marking the row `done` (a row that is no longer `prepared` is never credited again). The answer waits up to 8 seconds for a `pending` receive to finish.

Once the receiver has a record of the notes (any answer carrying one), the gateway drops the notes text from its row: `GET /receive/{notes_id}` is all it needs from then on, so the bearer notes are not kept on the gateway longer than the first call needs. A row ends `done`, `rejected` (refused, spent elsewhere, or given first by someone else) or `stuck` (below).

**Refusals: nothing was spent, the notes are still the holder's.**

| Answer | Why |
| - | - |
| `400 federation_not_joined` | The notes' federation has not been joined, has no row, or the notes name it by a short prefix that several joined federations share. Carries `fedimint: {federation_id, federation_prefix}` (`federation_id` is `null` when the notes do not carry it) |
| `400 federation_paused` | The operator paused that federation |
| `400 notes_unsupported` | Notes of a mint module the receiver does not take from that federation |
| `400 invalid_token` | Not notes the receiver reads, signatures that do not verify, or more than `FORGE_MAX_TOKEN_BYTES` |
| `400 amount_too_large` | The notes' face value is over the per-payment cap: `FORGE_FEDIMINT_MAX_SAT` (default 100,000 sat), or the federation's own lower `max_sat`. Carries `max: {sat}` |
| `400 federation_full` | Taking them would put the federation's holdings over its cap: `FORGE_FEDIMINT_FEDERATION_CAP_SAT` (default 1,000,000 sat), or the federation's own `cap_sat` |
| `400 insufficient_amount` | The federation's fee to take the notes is at least what they are worth |
| `503 fedimint_unavailable` | The receiver did not answer before anything was taken. Try again later. Only for notes the gateway has no top-up of: notes it has a row for are found by the id it works out itself (step 1), and answer what that row says. Notes it could not work out an id for (more than 256 notes, or text its reader does not read) still go to the receiver first, so for those this answer says nothing about an earlier top-up still `prepared` (the v2 app keeps such notes pending) |
| `409 token_in_flight` | The same notes are being taken by another request right now |

**Refusals after the receiver took a look.** `400 token_spent`: the notes were spent elsewhere first (the federation refused them), were given to the receiver first by someone else, or are already the top-up of another balance. Sending the same notes again to the same key is a replay (`replay: true`, nothing credited).

**The holdings cap** counts the receiver's balance for the federation, plus every Fedimint top-up of it still `prepared` or `stuck`, plus every one that ended `done` since that balance was read (it may or may not be in it, so it is counted: the check errs towards refusing). The count and the row's insert happen together, so two top-ups at once cannot both take the last room. Nothing is taken out of the receiver yet (take out stays Cashu, below), so its holdings only grow until the operator moves value out.

**Not known yet.** A `pending` record after the wait, no answer, or a `5xx` from the receiver answers `503 topup_pending` with the balance's `key` (when the gateway made it) and `account_id`, as a Cashu swap with an unknown outcome does. The row stays `prepared`. Startup recovery (the `startup_recovery` log line carries `fedimint_checked` and `fedimint_credited` while the feature is on) and a sweep every 30 seconds ask the receiver about every `prepared` row: `POST /receive` again with the same notes and key while the gateway still holds the notes (the receiver returns its record if the first call got through), `GET /receive/{notes_id}` after. Retrying the top-up with the same key and notes does the same at once. A receiver that answers `404` for a receive it had recorded has lost it: the row stays `prepared` and `fedimint_receive_missing` is logged for an operator.

**`issuance_failed`.** The federation took the notes but the receiver's new notes were not issued: value may be stuck. The top-up answers `502 issuance_failed` with the `key` and `account_id`, nothing is credited, and the row is marked `stuck` with the receiver's reason (`fedimint_issuance_failed` is logged as an error). The balance is kept even when empty (`releaseIfEmpty` leaves it), the sweep does not touch the row again, and `pnpm admin fedimint:list` counts it under `stuck`. The admin page lists it under Fedimint, Top-ups that need you ([ADMIN.md, Fedimint](ADMIN.md#fedimint)): **Check now** asks the receiver again and credits it once if its record has become `done` for this balance; once the operator has settled it with the person by hand, **Resolve** closes it for good (only while the receiver reports the receive `failed`), and the same notes sent again then answer `token_spent`. The person is never told the notes are lost.

**Crash safety.**

| The gateway dies | What is stored | What happens |
| - | - | - |
| before its row | nothing | Nothing reached the receiver; the notes are still the holder's |
| after its row, before `POST /receive` | the row, with the notes | Recovery posts the notes (the receiver has no record), then credits the `done` record once |
| after `POST /receive`, before the credit | the row (with the notes, or without once acknowledged) | Recovery reads the record (by `POST` again or `GET`) and credits `done` once |
| after the credit | the row `done`, the ledger line (`topup`, ref `fm:<notes_id>`) | Nothing left to do; the same notes again are a replay |

**Solvency: take out stays Cashu.** `POST /v1/wallet/refund` pays out Cashu from the gateway's wallet, as before, and never Fedimint notes. A sat balance funded with Fedimint notes is backed by those notes in the receiver's wallet, not by Cashu at the Forge mint. So the gateway's Cashu sat holdings can fall below what sat balances add up to. A take out the Cashu wallet cannot cover answers `503 wallet_insufficient` until the operator moves value from the receiver into Cashu (a rebalance). The admin page's Fedimint section shows sat balances against the Cashu sat held, warns when take out can fail, and suggests the amount to move; nothing moves it yet, because the receiver cannot pay a Lightning invoice ([ADMIN.md, Rebalance](ADMIN.md#rebalance-the-design)). `revenue:show` and the admin page count every sat balance against Cashu only, so they show less sweepable revenue, never more: Fedimint-funded balances are never exported as revenue.

**The v2 app** takes Fedimint notes in the eCash box, with Cashu, through the same `wallet.topup`: it reads them on the phone, sends nothing while `fedimint` is absent from the ways to pay or the notes are not from a federation it lists or are over its `max`, keeps them in the vault from before the request to the credit, sends pending notes again, and marks `issuance_failed` notes stuck. Every answer and what the phone keeps: [APP.md, Fedimint notes in the eCash box](APP.md#fedimint-notes-in-the-ecash-box).

Tested in `test/unit/fedimint.test.ts` against a stand-in receiver over HTTP (every branch above, a crash at each point, the timer, and notes sent again while the receiver is down, with real notes so the gateway's own `notes_id` is the receiver's), and end to end in `test/fedimint/topup.fedimint.test.ts` against the real receiver binary and real federations from its `devfed` binary ([FEDIMINT-RECEIVER.md](FEDIMINT-RECEIVER.md), Tests). Not covered by a test: `ambiguous_federation` and `issuance_failed` from a real receiver (the receiver cannot make either happen on demand; the stand-in covers the gateway's side), a federation of any real network, and a rebalance.

### A Fedimint card, through a till (the v2 Android app)

The engine runs no Fedimint client of its own. With the receiver turned on it takes Fedimint notes in a top-up (above), but a Fedimint card's notes reach it only through a till: fedimintcard's `till serve --pay-enabled`, whose pay route is documented in fedimintcard-pay `docs/PAY.md`, `POS-LINK.md` and `TILL-API.md`. The till charges the card and pays a Lightning invoice from its own wallet; to the engine this is an ordinary Lightning funding. The phone follows those documents (`public/v2/core/till.js`, the module `public/v2/modules/fund/fedimint/`):

1. **Pairing, once.** The till's owner runs `till pair --scope pay` and the person scans the QR code (or pastes its text, `fedimintcard-till-pay:<url>?t=<token>`). The Android app keeps the address and the pay token sealed with a key in the Android Keystore (`TillPlugin.kt`, ForgeTill) and adds the token to each request itself, so the page does not hold it after pairing. The app sends only `POST /v1/pay`, `GET /v1/pay/{id}?client_ref=`, `POST /v1/pay/{id}/refund` and `GET /v1/health`, and opens the card link. With no till paired the screen says first, before anything is tapped, "This card needs a till." and what a till does ("A till takes the money from the card and adds it to your funds."), then three numbered steps, each a picture and a few words: get the pairing code from the person who runs the till, scan it or paste it (paste it below, on a phone with no camera), then pay with the card. Scan is the lit button; once a code is pasted, Use this till is (with no camera it always is). Use this till with nothing scanned or pasted says "No pairing code yet." in the message line and puts the focus in the paste field (the button is never off). Once paired, the screen opens on "Till set." and what comes next ("Choose how much, then hold the card to the phone."), with the till's address, Change the till and Forget this till in its box under the amount. A till's own POS code (`fedimintcard-till:`) is refused, and so is plain http to another computer: the PIN and the token would cross the network in clear. The till must be on https (as the StartOS package is); http is taken only for this phone itself, for tests.
2. **The invoice.** `POST /v1/wallet/fund/lightning` for the amount, as the Lightning row does. The phone reads the invoice's amount from it.
3. **The price, before the tap.** The card is charged the invoice, the fee reserve the phone asks for (`max_fee_msat`: 2 sats and 0.5 percent of the invoice, in whole sats, at most the till's default cap of 1,000 sats) and the till's margin; a card whose notes cannot make exact change pays up to 2,048 msat more. The screen shows what reaches the funds, the most the card pays, and the most that goes to the till, and says that what the Lightning fees do not use stays with the till (PAY.md: the unspent reserve is not put back on the card). The pay token opens no route that tells the till's margin, so the phone takes it from the till's settings on the phone (0 unless the person enters what the till's owner set; 0 is the till's default) and from every answer the till gave before (`margin_msat`): a margin seen on one invoice bounds it on any other. Until the margin is known (the person saved it, or the till's answers showed one), the screen says the card pays that amount plus the till's margin if its owner set one; only then does it say "up to". If a till charges more than the price shown, the screen says so and the next price includes it.
4. **The tap.** The payment is stored on the phone (`forge2.tillpays`) and read back before the till hears of it, with a new `client_ref`. The person holds the card to the phone. The phone opens the card link (`/v1/card/link`, a WebSocket with the pay token) and sends `POST /v1/pay` with `X-Card-Link`, the invoice, `max_fee_msat`, the `client_ref` and the PIN, with a 130 second read timeout. Each card command the till sends down the link goes to the card (ForgeNfc) and its whole answer goes back; a card that leaves is reported `lost`. The phone never reads or keeps what passes. The PIN is held in memory for that tap only and is never stored.
5. **The answer.**

| Till says | What the phone does |
|---|---|
| `200 paid` | The till paid the invoice. The phone asks the engine for the funding until it is `done`, then the payment is removed. |
| `202 undecided` | The card paid, or may have. The phone asks the till (`GET /v1/pay/{id}?client_ref=`) and the engine until one says it is settled. Never another tap. |
| `502 pay_failed` | The invoice was not paid and the till holds what the card paid (`received_msat`), owed to the card. The screen offers Get it back: the same card behind a new link, `POST /v1/pay/{id}/refund`. A full card takes part of it (`refund_owed_msat`): spend from the card, then tap again. Another card is refused (`wrong_card`). The payment stays on the phone until the till answers `refunded`. |
| The card refused (`wrong_pin` with the tries left, `insufficient`, `no_card`, `card_link_gone`, `busy`, ...) | Nothing moved with this request. The next tap sends the same `client_ref`. A PIN the card refused is never sent again on its own. After an earlier request for the payment got no answer, the payment stays sent unless the answer carries the till's record of that `client_ref` (its `pay_id`, or `not_charged`): `card_link_gone`, `card_link_required`, `pay_disabled`, `bad_request`, `bad_invoice` and `lightning_unavailable` come before the till looks the `client_ref` up, so they say nothing about the earlier request, and the card may have paid with it. |
| Refused before the card was touched (`pin_required`, `invoice_expired`, `daily_cap`, `lightning_unavailable`, ...) | Nothing moved. A new `client_ref`, except after an unanswered request, as above: then the payment stays sent with its `client_ref`. There is one way out of that: `invoice_expired`, `wrong_network`, `over_limit`, `daily_cap`, `fee_reserve_too_low` and `pin_required` come after the till looked the `client_ref` up, and a pay that took or may have taken the card's money is answered from its record first. So one of them with no `pay_id` says the till holds no charge for the `client_ref`, as long as the unanswered request cannot still be charging the card beside it. The phone waits 130 seconds from that request for this (its card link lives at most 120). Sooner, the payment stays sent and the screen asks the person to wait two minutes and tap again. After that the payment is let go like any other refusal, so an invoice that ran out is dropped and a new one is asked for. `fee_reserve_too_low` gives the gateway's fee: when it is more than the reserve sent, the reserve becomes that, in whole sats, and the new price is shown before the next tap. When it is not (the till caps the reserve below the gateway's fee), the screen says this till cannot pay the invoice now. An invoice with less than 150 seconds left is not sent at all: the person sees the price again with a new invoice. |
| `401`, `403` | The till refused the pay token: pair again. |
| No answer, or `500` | The card may have paid. The payment is kept as sent; the next tap sends the very same request, which the till answers again without charging twice. The same holds when the phone cannot store the till's answer: the payment on the phone is still sent, and the screen says the till did not answer. |

A payment is tied to the till it was made through. While one is not finished, Change the till and Forget this till are off, and a payment made through another till is never sent to the one paired now (its `pay_id` would name another pay there): the row names the till it needs. A payment that waits on the engine or the till is looked at again when Funds opens, when the connection comes back and when the app starts. Erase everything warns about one that is not finished. Not covered: putting the unspent fee reserve back on the card (the till does not), a till that is offline (it refuses a pay), and an iPhone: the iPhone app reads cards but has no till part (ForgeTill is Android's), so Tap a Fedimint card is not offered there, and its address says "Fedimint cards need the Android app for now." with nothing to tap (the module's `unavailable`, shown by `screens/funds.js`).

Tested against a mock till that implements the documented routes, auth scope and states over real HTTP and a real card link (`test/support/mocktill.ts`), with a fake card. The mock stands in for the till alone: the Android plugins (`TillPlugin.kt`, `NfcPlugin.kt`) do not run in these tests. A real payment has been made by hand, once: a Pixel paired from the StartOS package's Pair a paying app, a real Fedimint card and its PIN, and the till paid the engine's invoice. A refund to the card through a real till has not been run.

## The gateway's wallet

Received proofs are stored in the `proofs` table with state `unspent`, `reserved` (selected for a payout in progress) or `spent`. The database is the wallet: back it up, and protect it like a hot wallet.

Payouts (change, refunds, revenue export) select proofs, and if no exact set exists, swap them into a send part and a kept part. All outputs are deterministic (NUT-13) from the gateway seed, with counters stored in SQLite, except the send part of a locked payout (below). Kept outputs are always deterministic.

### Locked payouts (NUT-11 P2PK)

A deterministic token can be re-derived from the gateway seed, so until the customer redeems it the gateway could spend it. A customer who gives a public key (`X-Cashu-Pubkey` on a NUT-24 request, `pubkey` on a refund or other-mint funding) gets a token whose send outputs are P2PK-locked to that key: secret `["P2PK", {nonce, data: <key>}]`, plain lock, no locktime and no refund keys (a refund key held by the gateway would bring back exactly the spending power the lock removes). The mint refuses to spend those proofs without a signature from the key, so the gateway cannot spend them at all.

- The key is stored with the payout (`outgoing.lock_pubkey`, and `requests.lock_pubkey` / `fundings.f_lock_pubkey` so change owed after a crash is still locked). It is not logged.
- A locked payout always swaps, even when an exact set of the gateway's proofs exists.
- Other-mint change and refunds are proofs at the token's mint, not the gateway's. With a key, those proofs are moved to a "pinned" payout (`outgoing.pinned = 1`) that swaps exactly them into locked outputs at that mint. The token's mint charges its input fee for that swap, so the locked token is worth slightly less than the unlocked one would be. If the fee would take the whole value, the proofs are handed over unlocked.
- Locked secrets are random, so NUT-13 restore by counter cannot find them. Recovery uses the stored preview instead (next section).

`pnpm admin revenue:export` sweeps eCash that is not backing customer balances or owed payouts into a token you can redeem elsewhere.

## Crash safety

Two mechanisms make every mint operation recoverable:

- **NUT-19 replay.** The serialized swap request (inputs and blinded outputs) is stored before the swap is sent. Replaying the identical request to a mint with a response cache returns the same signatures.
- **NUT-09 restore.** Outputs are derived from the seed and a counter range that is persisted before the request leaves. If the replay is not cached, the gateway asks the mint to restore signatures for that counter range.

### Receiving (topup or NUT-24 payment)

| Step | State written | If the process dies here |
| - | - | - |
| 1 | `incoming` row, `status=new`, keyed by a hash of the token's secrets (UNIQUE) | Nothing reached the mint. The row is deleted at startup; the client's token is still valid |
| 2 | counters reserved, swap preview stored, `status=prepared` | Startup recovery replays or restores; see below |
| 3 | swap sent to the mint | Same as 2 |
| 4 | one transaction: proofs stored, `status=done`, balance credited (or request marked paid) | Done exactly once |

Recovery of a `prepared` row: (a) replay the stored swap; (b) else restore the counter range and, if signatures come back, finalize with them; (c) else, if the input proofs are still unspent, perform the swap; (d) else the token was spent elsewhere and the row is rejected. Finalizing runs in one transaction that checks the row is not already `done`, so a topup is credited once even if recovery and a client retry race.

A second submission of the same token never reaches the mint twice: it finds the row. For a topup to the same key it returns `replay: true` with the current balance; anything else is `token_spent`. When a topup's outcome is unknown (mint timeout), the gateway keeps the new balance and returns its key with HTTP 503 `topup_pending`; retrying with that key and the same token completes it.

A NUT-24 request interrupted after payment (process died during the upstream call) is marked aborted at startup, and its full payment is owed back as change at `GET /v1/change/{request_id}`, the id from the 402 when the paid request echoed it. A NUT-24 request interrupted during its receive is marked failed at startup, after mint recovery has run: if its token never reached the mint, the token is still the payer's and the id answers `404`; if the swap's outcome is still unknown because the mint did not answer, the rule below applies.

A NUT-24 payment whose swap outcome was unknown when its request failed (a mint timeout, `mint_unavailable`, or a failure after the swap) is settled by whichever comes first: a retry with the same token, `GET /v1/change/{request_id}`, or the next startup. Recovery that finalizes the swap marks the request aborted and owes the whole payment back as change under that id at once. Until the mint answers, `GET /v1/change/{request_id}` returns `409 not_settled` with `Retry-After`, never `404`.

### Paying out (change, refund, export)

| Step | State written | If the process dies here |
| - | - | - |
| 1 | balance debited and `outgoing` row `status=owed` in one transaction (refunds) | The payout is owed; it is issued on the next refund call or change fetch |
| 2 | proofs marked `reserved` for this row, `status=reserved` | Nothing reached the mint. Startup returns the proofs and sets `status=owed` |
| 3 | counters reserved, swap preview stored, `status=prepared` | Replay or restore, as for receiving. Restored proofs are split into send and keep by matching the stored send-output secrets |
| 4 | one transaction: inputs `spent`, kept proofs stored, token stored, `status=done` | Done; the token is re-deliverable |

If the mint rejects a payout because the gateway's own proofs are already spent (a restored backup, for example), those proofs are marked spent and the payout goes back to `owed`.

### Locked payouts: recovery

The full swap preview, including the locked outputs' secrets and blinding factors, is stored (`status=prepared`) before the swap is sent. Recovery of a locked row:

1. **Replay** the stored request (NUT-19). The Forge mint and the test mints (Nutshell 0.22.1) cache `POST /v1/swap` for 7 days (`nuts.19.ttl = 604800`), so the same signatures come back and the stored secrets turn them into the same locked proofs.
2. If the mint refuses the replay, **restore by blinded message** (NUT-09): the stored blinded messages of every output are sent to `/v1/restore`. The mint returns the signatures it made for exactly those outputs. All signed: build the proofs from the stored secrets, finalize once. None signed: the swap never happened with these outputs, so the row is re-owed as an unlocked payout would be.
3. If neither works (no cache entry and restore refused or unsupported, or a partial answer), the outcome is **unknown**. The row stays `prepared`, counts as owed in `revenue:show`, gets `error = "outcome unknown: ..."` and the API answers `503 payout_unknown`. It is never re-owed and never paid a second time; every later issue attempt and every startup tries steps 1 and 2 again. If the mint never answers, an operator resolves it by hand from the stored preview.

Restoring by counter range (the unlocked path) is never used for a locked row: it would find only the kept outputs and hand over an empty token.

### Reservations

The gateway tracks in memory which reservations belong to requests it is still serving. A request owns its reservation from `reserve` until it settles; an error that escapes the request before settlement gives it up.

- At startup every active reservation is released without charge: a fresh process serves nothing, so each one is abandoned. A crash mid-request therefore costs the gateway the upstream bill for that request, never the user.
- A periodic sweep (every minute) releases, without charge, active reservations older than `FORGE_STALE_RESERVATION_SECONDS` that no request owns, and logs `stale_reservations_released`. A request still being served, such as a long stream, keeps its reservation however old it is.
- If a request settles after its reservation was released anyway, it is still charged what it used (capped at the reservation), up to what the balance covers after other active reservations. Any part the balance cannot cover is recorded as `shortfall_msub` on the reservation and logged as `settled_after_release`. It is never a silent zero charge.

`test/unit/ledger.test.ts` and `test/e2e/stale-reservation.e2e.test.ts` cover the sweep against a live stream, a late charge after release, the shortfall cap and abandoned-request cleanup.

### What these tests prove

`test/e2e/recovery.e2e.test.ts` injects a fault after the mint swap and before the database write, restarts the gateway on the same database, and checks the balance is credited exactly once (through replay and through restore), that a retry is idempotent, that an interrupted refund is recovered by restore and the token redeems at the mint, and that an interrupted NUT-24 request owes full change.

`test/e2e/p2pk.e2e.test.ts` checks locked NUT-24 change, refunds and other-mint change and refunds: the token's proofs all carry the key, a swap at the mint without a witness is refused, a plain wallet and the gateway's own wallet cannot redeem it, and the key holder receives exactly the amount. It crashes a locked refund after the swap and recovers it by replay, by restore of the stored blinded messages, and with both disabled (row stays owed, no second payout) followed by a restart that settles it once.

## Known limits

- One gateway process per database. In-process locks prevent concurrent use of the same token or payout; SQLite transactions guard balances.
- The seed sits in the database unless `FORGE_WALLET_SEED` is set. Losing both the database and the seed loses the wallet.
- Payouts come from one mint. With several trusted mints, a refund needs one mint to hold enough.
- Sub-unit balance remainders cannot be withdrawn.
- A change of units at the Forge mint pays an invoice of the Forge mint from the Forge mint in another unit. It works only where the mint's Lightning backends can make that payment (Changing units). The local test mints cannot show it.
- Fedimint-funded sat balances are backed by Fedimint notes at the receiver, while take out pays Cashu: take out can answer `wallet_insufficient` until the operator rebalances ([Fedimint notes](#fedimint-notes)).
- Other-mint funding trusts the token's mint for as long as the melt takes. A mint that takes the token and never pays leaves the funding in `melting`; the token's value is then lost to the user, as it would be with any wallet melting at that mint.
- A foreign mint's address is checked against private ranges when quoted, but DNS can change between that check and later requests (rebinding). The gateway sends such a mint only Cashu API calls.
- An on-chain address that receives a deposit after its watch window is not credited automatically. The quote stays at the mint; an operator can extend `expires_at` in `fundings` and set `state` back to `pending`.

## Checking quotes without tripping the mint's rate limit

Every funding's quote checks come from the gateway's one IP, and Nutshell allows 20 transaction requests a minute per IP. So:

- An unpaid Lightning quote is checked every 5 s for its first 2 minutes, then every 15 s to 10 minutes, every minute to an hour, and every 5 minutes after that.
- The status endpoint advances a pending quote only when it is due, however fast a browser polls.
- All quote checks share a budget of `FORGE_MINT_QUOTE_CHECKS_PER_MIN` (default 12).
- A 429 from the mint pauses every quote check for 60 s.
